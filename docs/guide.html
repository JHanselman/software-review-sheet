Background Guidelines for Writing and Reviewing Mathematical Software

How to perform a software review

Many mathematical papers now rely on code: to compute examples, to build databases, or as part of a proof. A software review checks that this code can be found, installed and run, and that it supports what the paper claims. This page is a practical companion to the review sheet and to the article Guidelines for Writing and Reviewing Mathematical Software.

The short version. Your main job is reproducibility, not checking the mathematics. Could an average user find the software, install it, run it, and check that the results are what the authors claim? Write down what you did, so the authors can follow your steps.

Section 1

Before you start

What you are (and are not) asked to do

  • You should be comfortable with the programming languages involved and broadly familiar with the field, but you do not need to be an expert on the topic of the paper.
  • You are not expected to check every line of code, nor to find every bug. The aim is to increase confidence in the results and to make sure others can reproduce them.
  • It is not your task to debug the authors' code. A quick fix is fine if the problem is obvious, as long as you report it.

Set yourself a time budget

Decide in advance how much time you will spend, for example an afternoon. If the installation is still failing when the time is up, that is a result in itself: stop, and report exactly where you got stuck. A review that says "I could not install this, and here is why" is valuable to the authors.

Licences for closed-source software

Code written for Magma, Maple or Mathematica can only be run with a licence. If you do not have one, tell the editor or organisers early; they may be able to find another reviewer. If you review the code anyway, say clearly in the review that you could not run it, so that "not tested" is not mistaken for "does not work".

Anonymity

Software reviews are hard to make anonymous. A repository usually reveals who the authors are, and opening an issue or pull request on it reveals who you are. Communicate through the editor unless you are happy for the authors to know who you are.

Section 2

The review, step by step

  1. Read the abstract and introduction, and skim the paper. What role does the code play: a new algorithm, a faster one, a database, examples, part of a proof? → sheet, part 5
  2. Make a list of the claims that depend on code. For each theorem, example or table: which file produces it, what output do you expect, and how long should it take? If the authors provide such a list, even better.
  3. Scan the repository. License, hosting, Readme, documentation, and what files there are. → parts 2 and 6
  4. Install the code and write down every step you take. → part 7
  5. Check what the authors recorded about their setup: versions, CPU, memory, running times. → part 8
  6. Run the tests and examples, then try to reproduce the claims from step 2. → parts 9 and 10
  7. Look at the readability of the code: documentation of functions, comments, indentation, naming, structure. → part 11
  8. Optionally, check the use of AI (see section 7). → part 12
Section 3

What kind of correctness?

Mathematics makes a sharp distinction between what is proven and what is merely very likely. Code can blur that line without anyone noticing.

Status of the results

Check what the paper claims about its results, and whether the code delivers that:

  • Proven or certified: every step is rigorous, using exact arithmetic or certified numerics (e.g. interval or ball arithmetic).
  • Conditional: correct assuming a conjecture such as GRH.
  • Heuristic: based on probabilistic algorithms or unproven bounds.
  • Numerical: floating-point results, possibly with recognition of exact values.

Common pitfalls:

  • Shortcuts taken by default. Computer algebra systems sometimes use heuristics unless asked otherwise. PARI's bnfinit, for instance, is only unconditional after a call to bnfcertify, and a Sage script can switch proofs off globally with proof.all(False).
  • Numerics. Is the working precision tracked? If an algebraic number is recognised from a numerical approximation, is it verified exactly afterwards?
  • Randomness. Is a randomised algorithm Las Vegas (always correct, random running time) or Monte Carlo (may be wrong with small probability)? Are seeds recorded so the run can be repeated?
  • Search bounds. For exhaustive searches and enumerations, check that the bounds in the code match the bounds in the paper. Mismatches and off-by-one errors are a real source of mistakes, and easy to check.

If the paper does not make the status clear, that is not necessarily a flaw in the code, but it is a good question to ask the authors.

Levels of reproduction

Record how far you got. This lets editors and readers interpret the rest of the review:

  1. Not attempted: e.g. no licence, or the code could not be installed.
  2. Tests or small examples ran successfully.
  3. Examples from the paper were reproduced.
  4. The full computation was rerun.

Nobody expects you to rerun a computation that took months. In that case, smaller examples, test files, verification files, or a second implementation can still give confidence that the results are correct.

Formal proofs

If the paper comes with a formalisation in a proof assistant (Lean, Coq, Isabelle, …), check that it contains no unfinished parts (such as Lean's sorry), which axioms it relies on (#print axioms in Lean, Print Assumptions in Coq), and above all that the formal statement says what the theorem in the paper says. A correct proof of the wrong statement is easy to miss.

Section 4

Running someone else's code safely

You will be running code you did not write, often with installation scripts that download more code. Mistakes are far more likely than malice, but a little care costs little:

  • Prefer a container or virtual machine (Docker, a VM, or at least a separate user account) over your everyday environment.
  • Read installation scripts before running them, especially anything that uses sudo or pipes a download straight into a shell.
  • Keep credentials (SSH keys, tokens, cloud accounts) out of reach of the code.
  • On shared machines, check how much memory and time a computation needs before starting it.
Section 5

Writing up the review

  • Be specific and reproducible. Give the exact commands you ran, the versions you used, and the full error message, not "it crashed".
  • Separate what must be fixed from suggestions. Use the for things that need attention, and say in the comments which problems you consider essential for publication.
  • Mention what is good. Authors put real effort into their code, and knowing what works is useful feedback too.
  • Report any changes you made. If you edited a file or a dependency to get things running, say exactly what you changed.
  • Be prepared for a second round. Many authors improve their code after a review. A short follow-up check of the accepted version is quick and very worthwhile.
Section 6

Using AI as a reviewer

AI assistants can make software reviews much easier, in particular when the code is written in a language you are less familiar with. They do not change who is responsible for the review: you are.

Confidentiality first. Uploading an unpublished manuscript, or a private repository, to an external AI service may break the confidentiality rules of the journal or conference. Check the policy before you do so. Public repositories and arXiv preprints are less of a concern, but the review itself is still confidential.

Good uses

  • Understanding code in an unfamiliar language.
  • Interpreting error messages and troubleshooting the installation.
  • Getting an overview of a large repository.
  • Drafting extra tests or independent verification scripts, which you then check yourself.
  • Polishing the wording of your review.

Be careful with

  • Reporting problems the AI found that you have not reproduced yourself. Invented bugs cost authors a lot of time.
  • Coding agents that keep patching the code until it runs. "It runs" and "it runs after these changes" are very different results.
  • Installation steps that only "the assistant figured out". Write down steps a person can repeat.
  • Agents running untrusted code with access to your files or credentials (see section 4).
  • Letting the AI judge whether the mathematics is correct.

Disclose what you used

A single sentence in the review is enough, for example "I used an AI assistant to help read the C code and to interpret error messages." The review sheet has a field for this (part 12).

Section 7

AI use by the authors

Using AI to write code, or even to find mathematical results, is not a problem in itself. As with any other tool, readers need to know it was used, and the output needs to be checked. Checking this is optional, but worthwhile:

Disclosure

Do the paper or the repository say where AI was used: for code, documentation, tests, or to produce results? Many journals and conferences now have a policy on this. A missing statement does not prove anything; if something is unclear, ask the authors rather than speculate.

Verification

  • Polish is not evidence. Clean code with good comments used to be a decent sign of careful work. AI-generated code often looks clean while being subtly wrong, so give more weight to tests, verification files and independent checks.
  • Mismatches. Look out for documentation that does not describe what the code actually does, and calls to functions that do not exist in the stated version of the software.
  • AI-generated results. If AI was used to produce results, for instance to search for examples or counterexamples, the model, its version and the prompts should be recorded. Most importantly, the results should come with something that can be checked independently of the AI, such as a certificate or a verification script.

The authors remain fully responsible for their code and results, however they were produced.
